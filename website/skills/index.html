How Tacomancy projects are run, made installable.

tacomancy/skills is a repository of agent skills distilled from Vitrine: the working practices that turned out to matter, each written so an agent in any other repository can follow it without Vitrine's context. One folder per skill, a SKILL.md in each, no build. Other repositories install them with npx skills add tacomancy/skills.

The repository the five specs

The five

Each one exists because a spec says what it does.

guidance-tiers Frozen and living documentation
A design document that must stay authoritative is frozen: never edited, indexed by a README that changes only with the folder's contents. Current understanding lives beside it and wins where it speaks; every divergence traces to an ADR. A check script, run as a required CI check, fails when the frozen tier is touched — a rule in a guidance file is only a rule if something fails when it is broken.
pin-prototypes Brief-driven design, pinned exports
One prompt per surface, each with what to push back on written before the output is seen. Exports pinned as numbered HTML and PNG. The brief wins on behaviour, the prototype on layout. A build-time rebrand that maps the design tool's palette onto the project's tokens as a total mapping, and fails on any colour it does not know.
adr-shape ADRs that name what they close
A lead paragraph naming the decision or open question this one closes. Every considered option priced with why it lost. The irreversible in the ADR, the reversible in the living architecture document, with a pointer each way. Superseded, never edited in place.
reversibility-rank What would be hard to change
Closes any round of recommendations with the hard-to-reverse items first, one line each on why they are sticky, and the rest marked trivial in a single line. Honest by construction: most rounds have one or two. Runs last in grill-me, grill-with-docs, and adr-shape, or alone on any list.
hidden-verify A desktop app checked without a window
An environment contract that makes the app render its window without showing it, capture after a delay, and quit; state pointed at a scratch directory so a run never touches the owner's; a driver over the DevTools Protocol that presses keys and reads computed styles, so proof is a value against a token, not a pixel.

How the repository is kept

The rules it holds itself to.

  • A spec before a skill. A skill exists because a GitHub issue labelled spec says what it does. Nothing is written without one.
  • A check that fails on unknown input stays a failure. No warn-and-continue mode, no default value that lets the unknown through.
  • Vendored skills are never edited. Extension goes through the new skill's own trigger, or one line in the adopting repository's guidance file.
  • Tests ship separately. tests/ mirrors skills/, so an install carries no test code. Every script a skill ships is tested as its user would run it: exit code, output, files — never from inside.
  • Nothing project-specific in the body. A Vitrine path or token appears only as an example labelled as one; the contract is stated generically first. Each SKILL.md ends with one Origin line naming the pattern it came from, so drift is visible later.

Where it stands

Specified, not yet shipped.

Five specs are written. guidance-tiers also lands the repository's skeleton — the test project, the structural checks, CI — so it goes first and is broken into tickets; the other four are blocked on it. When a skill lands, the install line above works for it.
