# 0016: The first Scout beat — arXiv, a Query-only Filter, due-on-open runs, and the minimal Queue that turns a Proposal into a stub

**Status:** Accepted

Beat 6 of the phase-1 map (#131) ships one Structured source and enough of the Scout Queue that a Proposal can be accepted into a Source stub. The brief's Scout system (`design-brief.md` § Scouts, § Scout Queue) assumes three things that do not exist yet: a Lexicon to compile Questions into search terms (its input turned out not to exist for CS/ML — research #132, decided in #144), accept history to rank on, and a second source to corroborate against. This ADR, from wayfinder ticket #138, decides what the beat is *without* them, so that nothing built now pre-empts those decisions. The shape: **arXiv** as the source; a Scout's Filter is a **hand-written arXiv query plus the Questions it is assigned to**, with "matched" meaning *assigned*, never *scored*; runs happen when the app is open and a Scout is **due**; the Queue ships its **two Lanes, the stack, keyboard triage, group-by-Scout, and reject-this-run**, and nothing that needs history; **health is derived from run rows** and a failed run is a state no quiet field can imitate. Everything else in § Scout Queue is on an explicit Wait list (decision 6) so its absence is a scope line, not an oversight. Field names, table columns, and the numbers are `docs/architecture.md` § Scouts.

## Decisions

1. **arXiv is the first Structured source.** It is where the user's field publishes first (Semantic Scholar and OpenAlex both ingest it, so starting upstream loses nothing); it needs no key and no metered account — the wrong thing to explain first in a BYOK app; its fields come back verbatim and complete in one Atom response, and where a field is absent (venue, keywords) it is absent at the source, which is exactly the "missing, not guessed" card the brief asks for; and its query language (`ti:`/`abs:`/`all:`, `AND`/`OR`/`ANDNOT`, phrases, `submittedDate` ranges) is one a Filter can be compiled into deterministically. The costs are accepted: no author keywords (true of every non-PubMed API), no venue on most cards, and publication date = first-submission date. OpenAlex was the runner-up and stays the growth-rate source for beat 10; as a second Scout source it adds venue through Corroboration later.
2. **A Filter is a Query plus assigned Questions; "matched" means assigned.** With no Lexicon there is nothing to compile a Tag or a Question's text into, so the Query — a hand-written arXiv `search_query` — does all the searching. The Scout is still **assigned** to Questions: they are stamped on every Proposal's Origin and on the accepted stub's `origin_question`, and they are what the coverage-gap row (beat 9) counts. No score stands behind the word, and the card says *assigned to*, not *matches*, so the day ranking arrives it is a new signal, not a redefinition. Compiling a Question's title words into terms as a stand-in was rejected: it is the Lexicon by another name, decided before #144 decides it. Tags are not a Filter in this beat.
3. **Runs are due-on-open plus an hourly check; one arXiv client for every Scout.** The core lives only while the app does (`docs/architecture.md` § Decided, core lifetime), so a Scout is *due* when now − its last completed run ≥ its cadence; the core runs what is due at vault open and on an hourly check while open, and each run's `submittedDate` window opens at the previous run's window end, so days the app was closed collapse into one run with nothing lost. *Run now* exists on the Scout. All Scouts share one arXiv client that serialises requests with the ToU's three-second gap on a single connection, so ten Scouts due at once queue rather than trip it. A `launchd` agent was rejected as the architecture already says: not until daily Scouts prove they want one. Manual-only was rejected because cadence would then be a recorded lie.
4. **A Scout is created by a small form in the Queue and stored as YAML read as found.** The form — name, arXiv query, cadence, assigned Questions, starting Lane, and a *try* action that sends the query once and shows the total and the first few titles — writes `.vitrine/scouts/<id>.yaml`. The file is read as found (ADR 0009's rule): a hand-edited Scout works, and one that does not parse is surfaced by name rather than skipped. Scout Activity (beat 9) edits the same fields in place; this form is the path until then. *Try* is there because a mistyped query returning nothing forever is the "broken looks like quiet" failure with the query as the source.
5. **The first run covers only since creation; a backward search is offered, never required.** Brief § Retroactive briefing, as written: the form offers *also search back to* a date, with a global default backstop, and the results carry `origin_retroactive` on the card and the stub so they can be triaged or rejected as a batch. Always-retroactive was rejected (a `cs.LG` query with no backstop is the whole archive); no-retroactive was rejected because a new Scout would then find nothing until tomorrow's announcement, which makes the beat impossible to demonstrate and the first day of every Scout silent.
6. **The Queue ships the mechanics that need no history; the rest is a named Wait list.** In: two Lanes, with the starting Lane set per Scout as the prior; Review as a stack (one card in hand, the rest listed underneath in order, nothing hidden); Skim as a single-line feed with an age cutoff past which lines are still reachable but not shown; keyboard triage — accept, reject, defer, next; grouping by Scout; sort newest; the "why this is here" panel reduced to what is true (Scout, assigned Questions, retroactive flag); *reject this run* as the one bulk action; hand promotion out of Skim (a line can be moved to Review, or accepted directly — lanes govern attention, not capability). **Wait,** each with the thing it needs: ranking signals and rank sort, the counterweight slot, promotion and demotion between Lanes by score, Review aging into a digest, muting, per-Scout ranking caps, bulk-defer (accept history); grouping by Question or topic cluster, Corroboration as a ranking signal (a second source or the Lexicon). Beat 6's spec grill does not reopen this list; a later beat's does.
7. **A Proposal is identified by its version-stripped arXiv id, and `doi` is stored for the next source.** `2409.01234v2` is the same work as `v1`: a revision is a new *appearance* on the same card, never a second card, and two Scouts whose queries overlap produce one card with two appearances. That is Corroboration's *mechanism* arriving for free within one source; the *signal* built on it still waits. `doi` sits on the row from day one so a second source can merge on it without a migration.
8. **Reject is permanent and silent; defer waits for the Scout's next run; next records nothing.** A rejected Proposal keeps its row, is never re-proposed (a `v3` lands on the rejected card), and is visible only in the Scout's log when beat 9 draws it. A deferred one leaves the stack until that Scout's next *completed* run and then returns at its position — "look again with the next batch", which is what the brief describes — and the prototype's third-defer-demotes waits with demotion. Skipping with *next* is not a triage event. Triage is an append-only log with timestamps, because accept rate *over time* is what beat 9 charts, and "reject this run" is one row per Proposal, not a flag on the run.
9. **Accept writes the stub the layout already fixes, with the abstract as its body and every assigned Question in `origin_question`.** The frontmatter is ADR 0006's (`docs/architecture.md` § Vault layout, Source / Source stub); `venue` and `keywords` are simply absent. The abstract as published is written once, at creation, as quoted lines — `createFile` is one whole write, inside the write discipline, and the app never touches the body again; a stub without it is a citation, not a record. `origin_question` is a list: the Scout was assigned to all of them. Nothing is written to any Question — an accept touching N Questions would be N app writes into user files, and for a Research Question would presume a side (supporting or opposing) the user has not chosen. Instead Coverage's definition is amended: an accepted stub's `origin_question` is an explicit edge, because the accept was a human act, which is what "explicit" means there.
10. **Source health is derived from run rows; a failed run is a distinct state.** For an API the brief's three fields become: last successful run (the request returned and the Atom parsed), last new item, and — in place of "structure change" — the last error with a kind: network, HTTP status, rate-limited, or parse (the response came back without the elements expected, which *is* an API's structure change). *Broken* means the most recent run did not succeed. None of it is stored on the Scout; all of it is a query over `scout_runs`, so Home, Loose Ends, and Scout Activity cannot disagree. "A reliably productive source gone unusually quiet" waits for run history to compare against (beat 9).
11. **Two guards, both visible.** Beyond *try* (decision 4): a technical ceiling per run, paged under the three-second gap, recorded on the run and shown on the Queue as *stopped at the ceiling — N more matched*. It is a safety limit, not the brief's per-Scout ranking cap, and it is deliberately loud so a broad query is a thing the user sees rather than a stack of thousands.
12. **This beat adds two Loose Ends rows and owes two Home items.** *Broken plumbing*: a Scout whose last run failed, with its error kind, resolving as *run now*, *pause*, or *open*. *Unfinished reading*: Source stubs with no PDF, oldest first, resolving through the existing *attach to a stub* flow (ADR 0013 decision 13). Home is beat 12; its *broken Scouts* and *Review depth* items are recorded as owed by this beat, not built here.
13. **One Scout event.** `scoutFinished { scoutId, runId }` is raised for every run, failed or not; the run row carries the outcome and the Queue invalidates its queries on it. A `scoutStarted` was rejected: runs last seconds and a "running…" line the user cannot act on is decoration.

## Considered options

- **OpenAlex or Semantic Scholar first.** Rejected, decision 1: a metered account or a shared anonymous pool, and reconstructed or "may be missing" abstracts, against arXiv's nothing-to-configure.
- **Query only, no Question links.** Rejected, decision 2: it severs the Scout ↔ Question edge the coverage-gap row and the stub's origin depend on.
- **A stand-in Lexicon from Question titles.** Rejected, decision 2.
- **`launchd`; manual runs only.** Rejected, decision 3.
- **Hand-edited YAML with no form.** Rejected, decision 4 — undemoable; but the file stays read-as-found so hand edits are not wrong.
- **Always retroactive; never retroactive.** Rejected, decision 5.
- **Shipping any ranking, muting, or aging now.** Rejected, decision 6: each needs history that does not exist, and a placeholder ranking would teach the stack a wrong order.
- **Skim with no age cutoff.** Rejected: a feed that only grows is the debt the brief designs against; the cutoff is display-only.
- **One card per arXiv version.** Rejected, decision 7.
- **Writing the stub into each Question's `related`, or into a Research Question's supporting list.** Rejected, decision 9.
- **An empty stub body.** Rejected, decision 9.
- **Health fields stored on the Scout.** Rejected, decision 10: three surfaces would then be able to disagree.
- **`scoutStarted`.** Rejected, decision 13.

## Consequences

- **+** Nothing in this beat has to be undone when #144 decides the Lexicon or when a second source lands: Tags join the Filter, ranking joins the sort, Corroboration joins the signals, and `doi` is already on the row.
- **+** A broken Scout — failed request, unparseable feed, mistyped query — is visible on the day it happens, at the Scout, on Loose Ends, and later on Home, from one source of truth.
- **+** The accept path exercises the whole spine early: Query → run → Proposal → stub in the vault → Loose Ends row → PDF attached → Ingest.
- **−** "Matched question" on a card means less than the prototype implies until ranking exists; the copy says *assigned to* so it does not overclaim.
- **−** Nothing runs while the app is closed. A daily Scout on a Mac that is opened weekly is a weekly Scout; the run window makes that lossless, not timely. The `launchd` question stays open with its stated trigger.
- **−** Skim-prior Scouts produce stubs only by hand promotion in this beat; the Skim feed is honest but quiet until ranking promotes for it.
- **−** `CONTEXT.md` § Coverage widens by one edge kind (decision 9), which the Question Map beat must count.
- The beat's spec carries: the form and *try*, the scheduler and shared client, the stack and feed, the four keys and reject-this-run, hand promotion, the stub write, the two Loose Ends rows, `scoutFinished`, and the health derivation. Its first ticket should be the run → Proposal → stub path with no Queue UI beyond the stack, because that is the tracer bullet.
