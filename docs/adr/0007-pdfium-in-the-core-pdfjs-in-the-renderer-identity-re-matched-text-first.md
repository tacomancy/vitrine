# 0007: PDFium in the core, PDF.js in the renderer, annotation identity re-matched text first

**Status:** Proposed — becomes Accepted when `prototype/pdf-roundtrip` passes the checklist in #108; anything it cannot make pass is added under Consequences before that happens.

ADR 0002 put annotations in the PDF with a sidecar for identity and left the re-matching mechanics abstract; ADR 0006 gave the sidecar a path and a `fingerprint` placeholder; `docs/architecture.md` § Open, item 1, asked for the engine and for what that placeholder holds. This ADR settles both after a `grill-me` pass. Because ADR 0005 puts file access in the core, "the PDF library" is two: **PDFium via WebAssembly (`@embedpdf/pdfium`, MIT) in the core**, which is the only thing that reads or writes a PDF, and **PDF.js (`pdfjs-dist`) in the renderer**, which only draws pages and provides a text layer to select from. The Reader never serialises a PDF: it sends the core an *annotation intent* — page, geometry in PDF user space, kind, colour, note — and the core writes the object, derives the quote, and assigns identity. Identity is re-matched on every Ingest in five tiers: object identity as a fast path that text must confirm, quote on the same page, quote anywhere in the document, geometry, then Unmatched. The sidecar stores raw values — the engine-extracted quote, the quads as written — and every normalisation rule and threshold lives in code, so tuning matching is never a migration. The field list and the tiers in full are `docs/architecture.md` § Annotation identity.

## Decisions

1. **The core owns the PDF; the renderer draws it.** One writer, one parser, one quote-derivation function, all in the core, where the tests already drive things without a window. The annotation intent the Reader sends is the same contract the phase-2 iPad PWA and a phase-3 native Reader (ADR 0003) send, which is what makes those a port rather than a re-implementation.
2. **PDFium, not MuPDF, on license grounds.** MuPDF's API is materially better for this job — per-glyph structured text, `highlight()` from a text range to quads, `update()` generating appearances, a true incremental save — and is AGPL-3.0 or a commercial licence. The repo is public with no LICENSE file; adopting MuPDF makes Vitrine an AGPL project permanently, since forks keep the licence even if the engine is later swapped. PDFium is BSD-3 and `@embedpdf/pdfium` MIT. The fork extension `EPDFAnnot_GenerateAppearance` closes the one capability gap that would otherwise have forced the choice: stock PDFium never writes an appearance stream on save, only when a page is rendered with `FPDF_ANNOT`. **MuPDF remains the named fallback**: if the prototype finds a gap the bindings cannot close, choosing it means adding an AGPL LICENSE at that moment, not buying a licence.
3. **Raw bindings behind one module.** `@embedpdf/pdfium`, not `@embedpdf/engines`: the wrapper's read path assigns a `/NM` to every annotation it sees — writing to the user's document as a side effect of looking at it, which Ingest must never do — and its save is full-rewrite only. The engine lives in a single `worker_thread` behind a job queue: WASM is single-threaded, a malformed PDF can trap it, and a trapped worker restarts and reports that one Source as unreadable instead of taking the core down.
4. **PDF.js renders only.** Direct `pdfjs-dist`, not `react-pdf`, behind one component of our own: page canvas, text layer, and Vitrine's overlay. Its annotation editor is unused (decision 1). The renderer draws the Annotations Vitrine owns — text markup and notes — as an overlay from the core's index, with the engine's rendering of those kinds suppressed, so identity, hover, selection, backlink counts, and the Unmatched marker attach to something the app drew rather than to pixels it has to reverse-map. Ink and shapes stay in the page bitmap exactly as the PDF has them; pencil fidelity is never redrawn by us.
5. **Which kinds are Annotations.** Text markup (Highlight, Underline, StrikeOut, Squiggly) and notes (Text, FreeText) get identity, a `^h<n>` block, and are link targets and `Q:` carriers. Ink and shapes are indexed with geometry-only identity so they round-trip and count on Ingest, but are neither link targets nor `Q:` sources: a geometry-only object is the one most likely to become Unmatched with nothing to judge it by, and keeping it out of the link path keeps that panel honest. Widening later is free; narrowing later orphans links.
6. **The core derives quote and quads from its own character boxes.** For a Reader-made highlight the renderer's selection text is a preview only; the core intersects the incoming geometry with the engine's per-character boxes, writes *snapped* quads — one per line of covered text — and stores the quote from the same characters. Preview-made quads are stored as Preview wrote them; Ingest never edits a PDF. Text tiers then compare engine-extracted text on both sides of every Ingest; had Reader-made quotes come from PDF.js's per-run text layer and Preview-made ones from the engine, the same passage could normalise differently and Vitrine's own annotations would fail its fast tier. A write whose derived quote is empty (a selection over an image or a scanned page) is refused with a plain message rather than stored quoteless.
7. **Five tiers, text before geometry, ambiguity is a decision.** (1) Object identity — the `/NM` Vitrine wrote — is a fast path that only skips a search when the quote also agrees; a disagreement falls through. PDFKit drops `/NM` on save, so expect this tier to fire only for Sources the iPad never touched. (2) Normalised quote on the same page; several text-equal candidates are broken by geometry overlap, and only an unbroken tie is Unmatched — otherwise every short highlight on a dense page is a decision on every Ingest, the dismissal-training failure the brief designed against. (3) The same quote elsewhere in the document, for a re-exported PDF whose pagination shifted. (4) Geometry: quad overlap above a threshold, same kind family; the tier for edited quotes, ink, and shapes. (5) Unmatched. For a note with no passage, its own `/Contents` is the text the tiers key on — the user's words are more stable than a position Preview lets them drag; an edited note falls to geometry.
8. **Store raw, normalise in code.** The sidecar holds the raw extracted quote and the quads as written, never the normalised quote or an IoU verdict. Normalisation (NFKC, line-break dehyphenation, whitespace, case) and the geometry threshold are code, tuned by the prototype and again after real use, without touching a Source. The one derived value persisted is the document fingerprint (decision 9), because recomputing it means opening every PDF.
9. **A replaced document is one event, not a storm.** The sidecar holds a document fingerprint — trailer `/ID`, page count, a hash of each page's extracted text. When it changes, Ingest reports *the document changed* as its own event, runs the tiers across the whole document, and groups the resulting Unmatched rows under that event with batch resolutions. Tier 3 exists for this case and is otherwise rarely needed.
10. **Removed is not Unmatched.** An identity with no inbound links that fails every tier is *removed*: its block leaves `## Annotations`, the sidecar entry stays with `removed_at` so the `^h<n>` is never reused, and the Ingest summary counts it without opening the panel. Inbound links — backlinks to `[[citekey#^h<n>]]` in the vault index, and any Question whose Provenance names the annotation — are what promote a disappearance from a count to a decision, per the brief's definition of Unmatched (§ Ingest review). A quote that changed under a geometry match keeps one level of history (`previous_quote`, `changed_at`), enough for the panel row to say what it was; quotes are not Positions and get no more.
11. **What Vitrine writes into an annotation it creates:** `/NM` = the sidecar id, `/T` = the user's name (Preview shows the author on every note; "Vitrine" there would be wrong), `/CreationDate`, `/M`, an appearance stream, standard `/Subj`. Nothing Vitrine-specific in `/Contents`.
12. **Incremental save, measured.** Appends can never corrupt the original content, and a 30 MB scanned PDF is not re-serialised for one highlight. Two facts weaken the case without overturning it: PDFium's incremental save re-emits every *loaded* object, not just dirty ones, and PDFKit rewrites the whole file anyway, so "prior bytes intact" is lost the first time the iPad touches a Source. The prototype measures growth per write; if it is pathological, a full-rewrite compaction past a size fraction is the one-line follow-up. Writes are atomic (temp file, rename). What happens when a write lands while the iPad holds the file open belongs to the watcher ADR (§ Open, item 3).

## Considered options

- **pdf-lib in the core.** Rejected: no text extraction at all, and Preview records no quoted text for a highlight — the quote must be reconstructed from quads against the page's character geometry, so the core engine must do positional text extraction, not just annotation parsing. It also writes no appearance streams.
- **PDF.js in the core.** Rejected: `getTextContent()` is per text run with no glyph boxes, and its writing path is a viewer that learned to save — the kinds its editor supports, whole-file rewrite.
- **MuPDF.** See decision 2. Named fallback, not rejected.
- **The renderer edits the document and posts the bytes.** Rejected: PDF bytes both ways across the socket and a second serialiser in play; the Reader contract stops being a port target.
- **The same engine on both sides** (PDFium-WASM in the browser) so geometry is computed identically. Unnecessary: quads are PDF user-space coordinates whichever side produced them, and decision 6 has the core re-derive from its own boxes regardless.
- **A packaged viewer with its own annotation UI** (EmbedPDF's viewer, Nutrient, Apryse). Rejected: a vendor UI would own the highlight interaction the brief specifies in detail (`design-prompts.md` Prompt 2).
- **Everything gets identity and is linkable, ink included.** Rejected, decision 5.
- **Any ambiguity is Unmatched.** Rejected, decision 7 — but an *unbroken* tie still is.
- **Notes match on the nearest line of page text.** Rejected: invents a relationship the PDF does not record.
- **Store the normalised quote.** Rejected, decision 8: every tuning of the rules becomes a migration across every Source, and any identity the migration cannot re-derive is a synthetic Unmatched storm.
- **Treat an unlinked deletion as Unmatched.** Rejected, decision 10: deleting your own unlinked highlight is not a decision waiting to happen, and making it one is how the panel gets clicked through.

## Consequences

- **+** One engine derives every quote and every written quad, so Vitrine's own annotations always pass their fast tiers.
- **+** Tuning matching is a code change; the sidecar never migrates for it. A `schema` bump (ADR 0006) is reserved for field changes.
- **+** The engine is behind one module in one worker; swapping it is a re-implementation of that module, and the repo's licence posture is untouched unless the fallback is taken.
- **−** Tier 1 is nearly useless for the Phase 1 reading path: PDFKit drops `/NM`, and does not bump `/M` on edit, so nothing Vitrine wrote survives a Preview save as an identifier. Text does the work, as the brief said it would.
- **−** A Preview-made highlight on a scanned page with no text layer gets identity (it is markup) but an empty quote, and lives on tier 4 alone. A Reader-made one is refused.
- **−** Highlight colour in the Reader comes from the sidecar: a recolour in Preview shows after Ingest updates the index, like everything else. The sidecar stores the PDF's colour verbatim; the overlay snaps to the nearest palette token; colour never enters matching.
- **−** PDFium's `SetColor` refuses once an appearance stream exists, so every edit regenerates the appearance; the fork extension is load-bearing and pins us to `@embedpdf/pdfium` rather than any PDFium build.
- **−** Incremental saves grow the file by the objects text extraction happened to load; the number is a prototype output.
- Whether a note edited in Preview to begin with `Q:` becomes a Question on that Ingest is an Ingest rule for the watcher ADR, not this one.
