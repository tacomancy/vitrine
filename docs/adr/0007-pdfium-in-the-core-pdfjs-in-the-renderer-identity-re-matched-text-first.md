# 0007: PDFium in the core, PDF.js in the renderer, annotation identity re-matched text first

**Status:** Accepted, 2026-09-20 — `prototype/pdf-roundtrip` (#108) ran all ten checklist items against a real two-column paper, on the Mac and on the iPad. No PDFium capability gap; MuPDF is not needed. What the prototype could not make pass as written is amended in decisions 5, 9, and 12 and recorded under Consequences; the numbers are in `docs/architecture.md` § Decided and § Annotation identity.

ADR 0002 put annotations in the PDF with a sidecar for identity and left the re-matching mechanics abstract; ADR 0006 gave the sidecar a path and a `fingerprint` placeholder; `docs/architecture.md` § Open (the PDF renderer and annotation library item) asked for the engine and for what that placeholder holds. This ADR settles both after a `grill-me` pass. Because ADR 0005 puts file access in the core, "the PDF library" is two: **PDFium via WebAssembly (`@embedpdf/pdfium`, MIT) in the core**, which is the only thing that reads or writes a PDF, and **PDF.js (`pdfjs-dist`) in the renderer**, which only draws pages and provides a text layer to select from. The Reader never serialises a PDF: it sends the core an *annotation intent* — page, geometry in PDF user space, kind, colour, note — and the core writes the object, derives the quote, and assigns identity. Identity is re-matched on every Ingest in five tiers: object identity as a fast path that text must confirm, quote on the same page, quote anywhere in the document, geometry, then Unmatched. The sidecar stores raw values — the engine-extracted quote, the quads as written — and every normalisation rule and threshold lives in code, so tuning matching is never a migration. The field list and the tiers in full are `docs/architecture.md` § Annotation identity.

## Decisions

1. **The core owns the PDF; the renderer draws it.** One writer, one parser, one quote-derivation function, all in the core, where the tests already drive things without a window. The annotation intent the Reader sends is the same contract the phase-2 iPad PWA and a phase-3 native Reader (ADR 0003) send, which is what makes those a port rather than a re-implementation.
2. **PDFium, not MuPDF, on license grounds.** MuPDF's API is materially better for this job — per-glyph structured text, `highlight()` from a text range to quads, `update()` generating appearances, a true incremental save — and is AGPL-3.0 or a commercial licence. The repo is public with no LICENSE file; adopting MuPDF makes Vitrine an AGPL project permanently, since forks keep the licence even if the engine is later swapped. PDFium is BSD-3 and `@embedpdf/pdfium` MIT. The fork extension `EPDFAnnot_GenerateAppearance` closes the one capability gap that would otherwise have forced the choice: stock PDFium never writes an appearance stream on save, only when a page is rendered with `FPDF_ANNOT`. **MuPDF remains the named fallback**: if the prototype finds a gap the bindings cannot close, choosing it means adding an AGPL LICENSE at that moment, not buying a licence.
3. **Raw bindings behind one module.** `@embedpdf/pdfium`, not `@embedpdf/engines`: the wrapper's read path assigns a `/NM` to every annotation it sees, so the next save writes ids into the user's document as a side effect of having looked at it — Ingest must never leave that trap armed — and its save is full-rewrite only. The engine lives in a single `worker_thread` behind a job queue: WASM is single-threaded, a malformed PDF can trap it, and a trapped worker restarts and reports that one Source as unreadable instead of taking the core down.
4. **PDF.js renders only.** Direct `pdfjs-dist`, not `react-pdf`, behind one component of our own: page canvas, text layer, and Vitrine's overlay. Its annotation editor is unused (decision 1). The renderer draws the Annotations Vitrine owns — text markup and notes — as an overlay from the core's index, with the engine's rendering of those kinds suppressed, so identity, hover, selection, backlink counts, and the Unmatched marker attach to something the app drew rather than to pixels it has to reverse-map. Ink and shapes stay in the page bitmap exactly as the PDF has them; pencil fidelity is never redrawn by us.
5. **Which kinds are Annotations.** Text markup and notes get identity, a `^h<n>` block, and are link targets and `Q:` carriers; ink and shapes are indexed with geometry-only identity so they round-trip and count on Ingest, but are neither link targets nor `Q:` sources (the table is `docs/architecture.md` § Annotation identity): a geometry-only object is the one most likely to become Unmatched with nothing to judge it by, and keeping it out of the link path keeps that panel honest. Widening later is free; narrowing later orphans links. *Amended by the prototype:* iPadOS Markup writes a pencil stroke as `/Subtype /Stamp` — an appearance stream plus PencilKit data in `/AAPL:AKExtras`, no `/InkList`, locked — so `stamp` belongs to the ink family: geometry-only identity from `/Rect`, rendered from its `/AP`, never a link target.
6. **The core derives quote and quads from its own character boxes.** For a Reader-made highlight the renderer's selection text is a preview only; the core intersects the incoming geometry with the engine's per-character boxes, writes *snapped* quads — one per line of covered text — and stores the quote from the same characters. Preview-made quads are stored as Preview wrote them; Ingest never edits a PDF. Text tiers then compare engine-extracted text on both sides of every Ingest; had Reader-made quotes come from PDF.js's per-run text layer and Preview-made ones from the engine, the same passage could normalise differently and Vitrine's own annotations would fail its fast tier. A write whose derived quote is empty (a selection over an image or a scanned page) is refused with a plain message rather than stored quoteless.
7. **Five tiers, text before geometry, ambiguity is a decision.** The order and rules are `docs/architecture.md` § Annotation identity; the reasoning: object identity (the `/NM` Vitrine wrote) is a fast path that only skips a search when the quote also agrees, so the brief's "text first" (§ Annotation storage) is never overridden by an id — and PDFKit drops `/NM` on save, so it fires only for Sources the iPad never touched. Text-equal candidates are broken by geometry overlap and only an unbroken tie is Unmatched, because otherwise every short highlight on a dense page is a decision on every Ingest — the click-through habit § Ingest review is designed against. A quote found on another page is a tier of its own because a re-exported PDF shifts pagination. A note with no passage keys on its own `/Contents`: the user's words are more stable than a position Preview lets them drag.
8. **Store raw, normalise in code.** The sidecar holds the raw extracted quote and the quads as written, never the normalised quote or an IoU verdict. Normalisation (NFKC, line-break dehyphenation, whitespace, case) and the geometry threshold are code, tuned by the prototype and again after real use, without touching a Source. The one derived value persisted is the document fingerprint (decision 9), because recomputing it means opening every PDF.
9. **A replaced document is one event, not a storm.** The sidecar holds a document fingerprint. *As proposed:* trailer `/ID`, page count, a hash of each page's extracted text. *As accepted:* page count plus a per-page similarity-tolerant text signature — the set of ≥4-letter words — compared by Jaccard with a threshold near 0.9; `/ID[0]` is kept as a fast "definitely the same file" check and never says "different". The prototype measured why: PDFKit's save replaces the permanent `/ID[0]` and re-encodes content so PDFium's extracted text differs afterwards (7 of 8 page hashes changed), which would have made every Preview save a document-changed event. Word-set similarity across that save is ≥ 0.95 on every page and ≤ 0.24 between neighbouring pages. When the fingerprint changes, Ingest reports *the document changed* as its own event, runs the tiers across the whole document, and groups the resulting Unmatched rows under that event with batch resolutions. Tier 3 exists for this case and is otherwise rarely needed.
10. **Removed is not Unmatched.** An identity with no inbound links that fails every tier is *removed*: its block leaves `## Annotations`, the sidecar entry stays with `removed_at` so the `^h<n>` is never reused, and the Ingest summary counts it without opening the panel. Inbound links — backlinks to `[[citekey#^h<n>]]` in the vault index, and any Question whose Provenance names the annotation — are what promote a disappearance from a count to a decision, per the brief's definition of Unmatched (§ Ingest review). That split reads `index.sqlite`, which ADR 0006 made disposable, so *removed* is concluded only against an index known to be current — Ingest refreshes it first — and an identity whose links cannot be established is Unmatched, never removed. A Tombstone (*drop the links*) is recorded in the sidecar and takes no further part in matching; without that, its still-live inbound links would re-raise it on every Ingest. A quote that changed under a geometry match keeps one level of history (`previous_quote`, `changed_at`), enough for the panel row to say what it was; quotes are not Positions and get no more.
11. **What Vitrine writes into an annotation it creates** is listed in `docs/architecture.md`; the two choices worth defending: `/T` is the user's name, because Preview shows the author on every note and "Vitrine" there would be wrong, and nothing Vitrine-specific goes in `/Contents`, because it is visible in every viewer.
12. **Full rewrite, always — the incremental save was measured and is pathological.** *As proposed:* incremental, because appends can never corrupt the original and a 30 MB scan is not re-serialised for one highlight, with a compaction rule if growth proved pathological. *As accepted:* `FPDF_SaveAsCopy` with the full-rewrite flag on every write, to a temp file then rename. PDFium's incremental save re-emits every object `FPDF_LoadPage` loaded — fonts, content streams, and on a scan the page image: 38–109 KB per highlight on text papers and 474 KB per highlight on a 2.3 MB scan, so five highlights doubled it. A full rewrite comes out the size of the original in single-digit milliseconds and keeps `/ID[0]`. A compaction threshold would have fired on every scan write, so it is the wrong shape. What the incremental save was for is still delivered: the temp-and-rename means a failed write never touches the original, and "prior bytes intact" was lost the first time the iPad touched a file anyway (PDFKit rewrites whole; it shrank the prototype's file from 570 KB to 312 KB). Incremental stays available for a file whose structure a rewrite would damage, if one ever turns up. What happens when a write lands while the iPad holds the file open belongs to the watcher ADR (§ Open, the ingest-trigger item).

## Considered options

- **pdf-lib in the core.** Rejected: no text extraction at all, and Preview records no quoted text for a highlight — the quote must be reconstructed from quads against the page's character geometry, so the core engine must do positional text extraction, not just annotation parsing. It also writes no appearance streams.
- **PDF.js in the core.** Rejected: `getTextContent()` is per text run with no glyph boxes, and its writing path is a viewer that learned to save — the kinds its editor supports, whole-file rewrite.
- **MuPDF.** See decision 2. Named fallback, not rejected.
- **The renderer edits the document and posts the bytes.** Rejected: PDF bytes both ways across the socket and a second serialiser in play; the Reader contract stops being a port target.
- **The same engine on both sides** (PDFium-WASM in the browser) so geometry is computed identically. Unnecessary: quads are PDF user-space coordinates whichever side produced them, and decision 6 has the core re-derive from its own boxes regardless.
- **A packaged viewer with its own annotation UI** (EmbedPDF's viewer, Nutrient, Apryse). Rejected: a vendor UI would own the highlight interaction the brief specifies in detail (`design-prompts.md` Prompt 2).
- **Everything gets identity and is linkable, ink included.** Rejected, decision 5.
- **Any ambiguity is Unmatched.** Rejected, decision 7 — but an *unbroken* tie still is.
- **Notes match on the nearest line of page text.** Rejected: invents a relationship the PDF does not record.
- **Store the normalised quote.** Rejected, decision 8: every tuning of the rules becomes a migration across every Source, and any identity the migration cannot re-derive is a synthetic Unmatched storm.
- **Treat an unlinked deletion as Unmatched.** Rejected, decision 10: deleting your own unlinked highlight is not a decision waiting to happen, and making it one is how the panel gets clicked through.

## Consequences

- **+** One engine derives every quote and every written quad, so Vitrine's own annotations always pass their fast tiers.
- **+** Tuning matching is a code change; the sidecar never migrates for it. A `schema` bump (ADR 0006) is reserved for field changes.
- **+** The engine is behind one module in one worker; swapping it is a re-implementation of that module, and the repo's licence posture is untouched unless the fallback is taken.
- **−** Tier 1 is nearly useless for the Phase 1 reading path: PDFKit drops `/NM`, and does not bump `/M` on edit, so nothing Vitrine wrote survives a Preview save as an identifier. Text does the work, which is the order § Annotation storage asked for.
- **−** A Preview-made highlight on a scanned page with no text layer gets identity (it is markup) but an empty quote, and lives on tier 4 alone. A Reader-made one is refused.
- **−** Highlight colour in the Reader comes from the sidecar: a recolour in Preview shows after Ingest updates the index, like everything else. The sidecar stores the PDF's colour verbatim; the overlay snaps to the nearest palette token; colour never enters matching.
- **−** PDFium's `SetColor` refuses once an appearance stream exists, so every edit regenerates the appearance; the fork extension is load-bearing and pins us to `@embedpdf/pdfium` rather than any PDFium build.
- **−** `/NM` survived on **0 of 9** Vitrine highlights after a PDFKit save on the Mac and again after the iPad's; `/T`, `/Contents`, `/QuadPoints`, `/CreationDate`, `/M`, `/Subj` all survived. Tier 1 is measured, not predicted, to fire only on files Preview never touched.
- **−** `FPDFAnnot_GetColor` refuses once an `/AP` exists, exactly as `SetColor` does; since every annotation Vitrine writes has one, the read path uses the fork's `EPDFAnnot_GetColor` from day one (opacity via `EPDFAnnot_GetOpacity`).
- **−** `FPDFPage_CreateAnnot` writes the annotation as a direct object inside `/Annots`. PDFKit re-serialises it as indirect on save, so the round trip holds, but a `/Popup` or `/IRT` can never reference one of Vitrine's annotations before that — fine for the kinds decision 5 gives identity to.
- **−** A quote containing a math glyph whose ToUnicode map was garbage to begin with (`¼` → `!`, U+0002 → `%`) fails tier 2 after a Preview save and lands on tier 4 with IoU ≈ 1 and a spurious `previous_quote`. Graceful; the panel row says what it was.
- **−** A sideways nudge over a narrow edge glyph (seen on a 10 pt Times paper, a 1.5 × −2 pt move clipping an "i") changes the quote by that glyph and drops the match from tier 2 to tier 4 with a one-character `previous_quote`. Degraded, not lost; loosening the 50 % glyph-coverage rule would start catching neighbouring glyphs instead.
- **−** On iPadOS: Markup has no sticky-note tool (a standalone note from the iPad is a FreeText box); a highlight cannot be moved, only copied or removed; and attaching a note to a highlight needed a hardware keyboard — Markup would not raise the on-screen one. The brief's phase-1 iPad claims hold: pencil fidelity is native, and a highlight whose note begins `Q:` becomes a Question (the note rides on the Highlight's own `/Contents` and its three-line quote reconstructs exactly from the iPad's quads) — "possible, awkward" is the honest status of typing it.
- Whether a note edited in Preview to begin with `Q:` becomes a Question on that Ingest is an Ingest rule for the watcher ADR, not this one.

## Update (2026-09-19, ADR 0013)

The two questions decision 12 and the last consequence handed to the watcher are settled there. A Vitrine write landing while the iPad holds the file produces a sync-service *conflict copy*; a new PDF whose document fingerprint (decision 9) matches an existing Source is a Loose end resolved as *use this copy* or *discard*, never a Source of its own. The `Q:` rule runs on every Ingest against the annotation's current note and spawns a Question once — the sidecar gains a `question` field per annotation — so a `Q:` added in a later Preview pass becomes a Question on that Ingest.
