# 0039: The Scout Queue keeps what `queue.sqlite` cannot rebuild — held, interrupted, and batched are rows, not flags

**Status:** Accepted

The spec grill for beat 6 (#173), run on 2026-10-01 against ADR 0016 and ADR 0032, found seven places where the written design either left a case open or would have quietly lied. Each answer lands in a table that `docs/architecture.md` § Index calls the one database that is never deleted: `queue.sqlite` has no rebuild path (ADR 0006 decision 10), so a column or a state added after rows exist cannot be recovered from the vault. That is why these are recorded as a decision rather than left to § Scouts. The rule each one follows is the same: **what the researcher did, or what the machine could not do, is a row; nothing is inferred later from the absence of one.** Field names, numbers and sentences are `docs/architecture.md` § Scouts.

## Decisions

1. **A Proposal for work the vault already holds is *held*, not proposed.** ADR 0016 decision 9 writes a stub per accept and never asks whether the work is already there — the usual case for anyone who hand-attached a paper before creating the Scout, and the case a crash between the stub write and the `proposals` update produces. `proposals.state` gains `held`: its `source_key` (ADR 0017) matches a `doi` or an arXiv-normalised `url` on an existing Source or Source stub. The match is exact on the key, never fuzzy on titles. It runs when the Proposal arrives and again **inside the accept function**, so a caller cannot forget it and a crash-orphaned stub is *adopted* — `stub_path` set, no second file — rather than duplicated as `schreiner2026a.md`. A held Proposal is never a card, writes no `triage` row, and is invisible to Accept rate; it is counted on the run and on the Scout's group, *already in your vault*, each linking to the file, so it is neither hidden nor silent. Nothing is written to the file it matches, for decision 9's reason.
2. **A run that never finished is closed as failed, `interrupted`.** `scout_runs.outcome` is `ok | failed`, and health reads the newest run. A quit, a crash or a closed lid leaves a row with `started` and no `finished`, which the query would pass over — and a Scout whose last real run was long ago would read as quiet or as never run. On core start any such row is closed as `failed` with `error_kind = interrupted` and the sentence *Vitrine closed before this check finished.* It retries at the next check and does not advance `window_to`. Deleting the row was rejected: a request that crashes the core every time would then leave no trace anywhere.
3. **Retry depends on the kind of failure.** ADR 0016 decision 3's *due* reads the last *completed* run; a failed one is not, so read literally every failure is due at every hourly check. `network`, `http` and `interrupted` retry at the next check. `rate_limited` and `parse` wait a full cadence from the attempt — asking again sooner gets the same answer, and the first is the wrong direction against a ToU that asks for restraint — and *Run now* or editing the Query overrides both. `CONTEXT.md` § Due says so.
4. **Only a Proposal the Scout placed in Review counts toward Accept rate.** Decision 6 lets a Skim line be promoted by hand and then accepted; if promotion simply moved the row to Review, every such accept would inflate the rate with the researcher's own cherry-picking, and beat 9 reads that rate to say a brief is bad. The `promote` row in `triage` is the marker, so no column is added. A hand-promoted accept still writes its stub.
5. **A bulk reject says it was one.** *Reject this run* writes one `triage` row per Proposal (decision 8), and each counts. That is right for *this run was junk* and wrong for clearing a retroactive search because the backward search was not wanted, which says nothing about the brief. `triage` gains a nullable `batch` — the run id — set only by that act. Every row still counts; beat 9 may exclude batched retroactive rows without a migration, and this ADR does not decide that.
6. **Undo exists for reject and defer, and not for accept.** ADR 0016's update of 2026-09-26 left undo to the beat that first ships one for a machine proposal. In the Queue it is a compensating `triage` row, so the log stays append-only and Accept rate stays correct, and it lasts for as long as the card is in this session's stack, like Loose Ends' (#266). Undoing an accept would mean the app deleting a vault file it wrote, which `CLAUDE.md` § Invariants forbids by its first line; a wrong accept is fixed in the vault by the researcher. `P` pass puts the card at the bottom of this session's stack and records nothing, so the order is newest-first again on the next open.
7. **A Scout file that does not parse is a broken Scout.** ADR 0016 decision 4 says it is *surfaced by name rather than skipped* and not where. It appears in the rail by file name in the *wrong* voice with one sentence naming the line, and as a *Broken plumbing* row whose only resolution is *open*. It has no `error_kind` — no run exists to carry one — so it is a second derivation into the same voice, not a sixth kind. A file the app cannot read must not look like a Scout nobody made.

## Considered options

- **Showing a held Proposal as a card with *accept* disabled.** Rejected, decision 1: it asks the researcher to pass or reject a card the app knows is not a decision, and a reject would pollute Accept rate.
- **Fuzzy matching on title for held.** Rejected: a false positive hides a new paper, and the only warrant for hiding is an identical key.
- **Deleting an unfinished run.** Rejected, decision 2.
- **Retrying every failure hourly; never retrying a failure.** Rejected, decision 3: the first hammers an endpoint with the same malformed query, the second makes a transient outage permanent until *Run now*.
- **Moving a promoted Proposal to Review and counting it.** Rejected, decision 4.
- **Excluding batched rejects from Accept rate now.** Rejected, decision 5: which rows to exclude is beat 9's question, and a column recorded now keeps it answerable.
- **Undo for accept by deleting the stub.** Rejected, decision 6.
- **Resuming a truncated retroactive search on later runs.** Rejected for this beat, not recorded as a decision: it makes `window_to` mean two things and turns one search into a multi-day crawl. It is on the Wait list with that trigger.

## Consequences

- **+** Every state a Proposal or a run can be in has a row that says so, so a surface cannot disagree with another about it — the same shape as ADR 0016 decision 10 and ADR 0032 decision 7.
- **+** A crash between a stub write and its record repairs itself on the next accept or arrival instead of producing a duplicate.
- **+** Beat 9 can chart Accept rate with or without batched rejects, and with or without promoted accepts, from the log alone.
- **−** `queue.sqlite` moves to schema version 4 for the Scout tables; the migration is additive, and the file still has no rebuild path.
- **−** `interrupted` makes an ordinary quit during a run a *wrong* state for the seconds until the vault is next opened and the retry lands; it is the price of a killed request being visible.
- **−** A Proposal can be *held* by a stub that carries an arXiv `url` the user typed differently; normalisation is the one place a false negative is possible, and it errs toward showing a card.
