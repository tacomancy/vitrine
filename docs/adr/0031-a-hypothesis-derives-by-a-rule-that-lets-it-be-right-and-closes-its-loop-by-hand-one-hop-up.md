# 0031: A Hypothesis derives its state by a rule that lets it be right, and closes its loop by hand, one hop up

**Status:** Accepted

Beat 3 of the map (#131, beat issue #170) is the first code to derive a state, the first to write a result into another object on a Hypothesis's behalf, and the first to guard a record against post-hoc storytelling. The brief (§ Testing: Hypothesis and Experiment) and `CONTEXT.md` § Testing gave the mechanics in prose; stories TEST-1 to TEST-7, CAP-5 and REP-9 in the story tree gave the tests. Printing the derivation rule beside the state (TEST-3) is what exposed the one defect here: the brief's rule, read literally, can never return *supported* for a hypothesis that has a falsifying criterion. A `grill-with-docs` pass on 2026-09-28 settled the rest; the detail is `docs/architecture.md` § Vault layout (Hypothesis) and § Hypothesis view, and the vocabulary is `CONTEXT.md` § Testing.

## Decisions

1. **The derivation rule is corrected, not transcribed.** *Falsified* when any falsifying Criterion is met. *Supported* when none is, every confirming Criterion is met, every falsifying Criterion is *not met*, and there is at least one of either. Otherwise *inconclusive*. Diagnostic Criteria never decide. The brief's "all criteria met → supported" makes a falsifying Criterion a trap: met kills the claim, and not met — the claim surviving the test written to kill it — fails "all met", so writing the most honest criterion there is makes the claim impossible to support. It also let an unmet sanity check block support although a diagnostic Criterion is defined as not deciding. A Hypothesis with no Criteria, or only diagnostic ones, is inconclusive, never vacuously supported. The page prints the rule in these words, *diagnostic criteria never decide* included.
2. **Awaiting evidence is the absence of an Outcome, not a fourth value.** A Criterion with no `outcome::` line is *awaiting evidence*; the three Outcomes are unchanged. This is what makes TEST-4 structural: a Criterion cannot read *tested and inconclusive* unless someone typed `inconclusive`. Whether Evidence is attached is a separate fact, and a Criterion with an Outcome and nothing attached says so.
3. **A Criterion's number is permanent, and its label is derived from it.** The label is the Relationship's letter plus the number of its `^c<n>` block id — `F1`, `C2`, `D5` — so changing a Relationship changes only the letter, nothing ever renumbers, and the label is the anchor a wikilink uses. A number is never reused, even after its Criterion is deleted: the next one is one past the highest in the file *or* in its `## Position history`, which names every Criterion that has ever existed. Nothing new is stored. A history entry records the label as it stood; because the digit is the id, that is enough to resolve it.
4. **A Criterion's whole block is one Position; only text or Relationship after evidence is marked.** Every change to a Criterion — text, Relationship, Outcome, Evidence — is a Revision, so recording an Outcome or detaching a run leaves a trail. A change to the text or the Relationship while Evidence is attached is *Edited after evidence*: permanent on the Criterion, with the old wording readable, and never collapsed in the history. Recording an Outcome is never marked, because it is what Evidence is for. A Relationship is chosen when a Criterion is written, with no default; one missing from the file does not count yet — it blocks *supported* and cannot falsify.
5. **A Criterion with Evidence is taken out of the rule by making it diagnostic, not by deleting it.** Diagnostic already means "does not decide", so no *withdrawn* marker is needed; the change is a Relationship change and earns the mark from decision 4, on the page where a reader will see it. Before Evidence exists a Criterion is a draft and deletes freely. A deletion made in Obsidian is caught by the watcher and recorded as an entry that never collapses.
6. **Each move of the Derived state is a history entry.** The state is never stored, but *when the rule began returning a different answer* is a fact no later recomputation can recover. It is also the only place the falsification date lives. When a corrected Outcome moves the state back, the old entry stays and a new one joins it.
7. **An Override is narrow, and anything it judged voids it.** *Inconclusive → supported* only, and only once at least one Criterion carries an Outcome — before that there is nothing to be partial about, and an Override would simply be declaring the state. It is voided by any later Revision of a Criterion, by a Criterion added or deleted, or by a Revision of the claim; never by design notes. The void is its own entry, and a new Override needs a new why.
8. **Closing the loop is an act, it reaches one hop, and it never edits a line it wrote.** The state is derived live; writing it back is the user's decision, because it writes into another file and the state can move again. The act becomes available when the state is *supported* (an Override included, and the line says so), when it is *falsified*, and when it is *inconclusive* with every Criterion carrying an Outcome — *tested and undecided* is an answer, *not yet tested* is not. It writes to the object the Hypothesis was promoted from and stops. A Question becomes *answered*; a Research Question gains the line and keeps its Status, because a test of a sharpened claim has not answered the broader question. This amends `docs/architecture.md`, which had the write reach every Research Question in between; the frozen prototype had already drawn the parent as *updated by this result*. Nothing is stored on the Hypothesis: whether the loop is closed is read from the line in that one object. If the state later moves, the page says the line no longer matches, and closing again appends a new line. A Hypothesis promoted from nothing has no loop to close, and one whose parent no longer resolves has the write refused with the reason; the follow-up capture (CAP-5) is offered either way.
9. **Promotion asks for the claim and nothing else, from a Question or from a Research Question.** A question cannot be turned into a falsifiable statement by copying its words, so promotion is one typed line — `h` on an open Question in the Inbox, or the same line beside *resolve* on a Research Question page — after which the page takes the keyboard. Criteria are written on the page. A Research Question that spawns a Hypothesis stays *open*, gains a line under its related questions, and drops out of the stalled-source row, since spawning a test is the opposite of going quiet. The file is named from the claim at promotion and never renamed when the claim is revised; the claim's history lives on the page, and on screen the Hypothesis is named by its current claim.
10. **This beat attaches no Evidence; Evidence lines are read as found.** Runs arrive in beat 4, where attaching gets its subject (TEST-12). Until then a `- [[x]] — what it shows` line under a Criterion is Evidence whether or not its link resolves, exactly as beat 2 reads a hand-written source line. That is enough for decision 4's mark to guard Criteria from the moment they exist rather than from a beat later.
11. **Two capture contexts are defined.** `resolving` is the follow-up captured as a loop is closed. `pursuing` is extended from a Research Question's page to a Hypothesis's: a sub-question of it. The Hypothesis gets no related-questions section — its related rail is derived from `promoted_from` and from the Questions whose `from:` names it.

## Considered options

- **Transcribe the brief's rule.** Rejected (decision 1): it is the rule the printed-rule story exists to let a reader check, and a reader would find it broken.
- **`outcome:: awaiting` as a stored fourth value.** Rejected: it adds a value the brief does not have, and it lets *awaiting* and *inconclusive* differ only by what someone typed.
- **Labels numbered per Relationship in file order,** as the prototype draws them (`F1 · C1 · C2 · C3 · D1`). Rejected: deleting a Criterion renumbers the rest, so a label in the history would name a different live Criterion. A stored per-Relationship counter was rejected too: it needs new state, and a new number whenever a Relationship changes.
- **Only a Criterion's text as its Position.** Rejected: an Outcome flip or a detached run would leave no trace, and "evidence exists at the moment of the edit" could be evaded without anyone seeing.
- **Write-back fires the moment the state leaves *inconclusive*.** Rejected: a write into a second file on the far side of an Outcome edit, including one made in Obsidian, and a Question answered, un-answered and answered again by a Criterion corrected twice.
- **Write-back reaches every object up the chain.** Rejected (decision 8).
- **Editing or retracting a Write-back line when the state moves.** Rejected: the line is true of its date; rewriting it deletes a record from the user's file.
- **A *withdrawn* marker for Criteria.** Rejected (decision 5): diagnostic is already that.
- **One key promotes with an empty claim, or promotion asks for Criteria too.** Rejected: the first writes a file the app cannot name; the second contradicts the prototype's own fresh state, criteria "written the same afternoon".
- **A minimal attach over any vault file in this beat.** Rejected: its subject is wrong, and beat 4 would rewrite it.
- **A second Loose Ends row for a tested result never written back.** Rejected: it is the nag the brief rules out.

## Consequences

- **+** The state printed on the page is a function a reader can check against the Criteria and find correct, and the rule rewards writing a falsifying Criterion rather than punishing it.
- **+** Every guard against post-hoc storytelling — the mark on an edited Criterion, the void on an Override, the entry for each move of the state — lives in the file, reads in Obsidian, and needs no App state.
- **+** No Status is written by anyone but the user or its own page: the Hypothesis stores no state, the Question is answered only by an act, and a Research Question's Status stays the Research Question's.
- **−** Decision 1 departs from the frozen brief and the frozen prototype's printed rule. Anyone reading them without this ADR will see a different rule than the app prints.
- **−** Decision 3's labels read `F1 · C2 · C3 · C4 · D5` rather than the prototype's tidier run.
- **−** Decision 10 means edited-after-evidence can only be demoed in this beat by writing an Evidence line in Obsidian; the app's own attach is beat 4's.
