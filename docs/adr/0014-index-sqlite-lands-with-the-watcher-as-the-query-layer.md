# 0014: `index.sqlite` lands with the watcher's Markdown consumer, via `node:sqlite`, as the query layer for every surface

**Status:** Accepted

Three accepted ADRs already assume an index without ever deciding it: ADR 0006 decision 10 names `index.sqlite` as "the vault index and full-text search — always safe to delete"; ADR 0013 decision 4 puts the Markdown side's `{ size, mtime, hash }` record in it and decision 10 reads a Position's previous text "from the index before the first change"; ADR 0007's tier 5 concludes *removed* only against an index "known to be current". Meanwhile #120 resolves links by walking the whole vault per call and `questions.list` walks it again. Wayfinder ticket #137 asked which beat forces the index and what it holds. Settled after a `grilling` + `domain-modeling` pass: **the index lands with the first watcher ticket** — a new beat 1b between the Markdown reader/writer (#117) and the Research Question view — **on Node's built-in `node:sqlite`**, holding everything the outline already yields except body text, and it is **the read path for every surface**: lists, counts, backlinks, and resolution come from it, while a single file is read from disk only to display or write it. It stays disposable: any schema mismatch or open error drops the file and rebuilds in the background.

## Decisions

1. **SQLite, through `node:sqlite`, on disk at `.vitrine/index.sqlite`.** Verified: Electron 44 ships Node 24.21, whose `node:sqlite` loads in the core's utilityProcess and creates FTS5 virtual tables. So the index costs no native module — the line ADR 0013 decision 2 drew holds — and no dependency. An in-memory index rebuilt at open was rejected: it is enough for today's few hundred files and has to be replaced the moment full-text search or ADR 0006's "tens of thousands of files" arrives, and every launch would re-outline the vault. `better-sqlite3` was rejected as the repo's first native module, rebuilt per Electron ABI, for nothing the built-in lacks.
2. **The watcher's Markdown consumer is the beat that forces it.** ADR 0013's first ticket ("Markdown-side: the Inbox goes live") needs a per-file stat record to sweep against and the pre-change Position text for a pending Revision; both are index rows. Beat 2 (Research Question view, Loose Ends shell) needs backlinks and vault-wide resolution; beat 5 (Reader) is only the first place a *stale* index does silent harm. Landing it at beat 2 would make the watcher ticket build a throwaway in-memory record that beat 2 replaces; landing it at beat 5 would leave three beats walking the vault per call. So: **beat 1b, its own spec** — watcher, index, and `questions.list` / `vault.tags` re-based onto the index — demoable end to end (edit a Question in Obsidian and the Inbox updates; rename a Note and its links' resolution follows; delete `index.sqlite` while the app runs and nothing visible changes). It touches the load-bearing watcher, which `CLAUDE.md` § Parallel work says to sequence, so it is cleaner as its own branch than buried in the Research Question view's.
3. **Query layer, with one rule.** Every list a surface shows — Inbox rows, the tag tree, backlinks, Loose Ends counts, Coverage — is a query over the index. A file is read from disk to display its body or to write it, and **a write is never based on the index**: § Markdown's protocol already re-reads and re-hashes the file for `basedOn`, so the index cannot be the thing a write trusts. The alternative — surfaces keep reading files directly and the index answers only what one file cannot — was rejected because every surface then carries its own walk, and Coverage and Loose Ends would be the third and fourth.
4. **Day one holds the whole outline except body text.** Files (`path, size, mtime, hash, kind, id`), the frontmatter keys the app reads per Kind, headings, block ids, links with their resolution state, tags with source and position, inline fields, and the current text of each Position. Not day one: full-text search and section bodies. The marginal cost of storing an outline row is near zero once the file is being outlined; a table skipped now is a schema touched later.
5. **Normalised tables, one per outline concept, every row carrying `path`.** Backlinks, tag counts, and Coverage are plain `SELECT`s. A JSON outline blob per file with a couple of derived tables was rejected: every cross-file question would unpack JSON.
6. **Positions come from the per-Kind modules, not the outline.** The outline does not know that `## Working answer` is a Position and `## Open threads` is not. After outlining, the indexer calls the Kind's `positionsOf(outline, content)` and stores what comes back in a `positions` table (`path, field, text, hash`). This keeps "which sections are Positions" in the one module that will also write the Revision, and keeps generic section bodies out of the index (decision 4).
7. **Markdown only.** The sidecar remains the sole record of a PDF (ADR 0013 decision 4); the Source note's `## Annotations` blocks are outlined like any other block id, so `[[citekey#^h12]]` backlinks resolve through the `blocks` and `links` tables. Tier 5 asks the index "who links to `citekey#^h12`" and nothing else.
8. **Incremental refresh, per batch, in one transaction.** A watcher batch (ADR 0013 decision 5) re-outlines its changed files and replaces their rows — `DELETE … WHERE path IN (…)`, re-insert; a vanished path deletes its rows. Link resolution is a derived column recomputed by query in the same transaction for every link whose target basename the batch touched, so a rename, create, or delete never re-outlines the files that pointed at it. At open, the sweep (ADR 0013 decision 3) compares stats to the `files` table and re-outlines only the differing files. A full rebuild happens only on schema mismatch or corruption (decision 10).
9. **`vaultChanged` fires after the commit.** ADR 0013 decision 11's `vaultChanged { paths }` is raised by the code that committed the batch's transaction, never on settle, so a surface invalidating queries reads the new rows. The same holds for `ingestLanded` relative to the `## Annotations` rewrite's index update.
10. **Disposable at every schema change; indexing never blocks the window.** The schema number is `PRAGMA user_version`, a code constant independent of `vault.json`'s `schema` (which versions the vault layout, ADR 0006). A mismatch or an open error drops the file and rebuilds. The app opens at once and indexes in the background; surfaces show a quiet "indexing…" line in the same footer channel as the Inbox's unreadable count — no modal, no progress ring — and the index reports itself not current until the rebuild finishes (decision 11). WAL journal mode; its `-wal`/`-shm` siblings live under `.vitrine/`, which the watcher already drops. On vault open the app writes `.vitrine/.gitignore` containing `index.sqlite*` if the file is absent — the one disposable file, never `queue.sqlite` or the sidecars.
11. **"Current", for tier 5.** The index is *current* when the open-time sweep has completed, the watcher is healthy (no unrecovered error or overflow), and every Markdown batch that settled before this Ingest run started has been applied. Ingest flushes pending Markdown batches before tier 5 runs (§ Annotation identity: "Ingest refreshes it before this tier runs"); a Markdown file still inside its settle window is *not* waited for. The module exposes `current()` with the reason when false, and when false tier 5 says Unmatched, never removed — the cheap failure ADR 0007 prefers.
12. **Full-text search joins with the Vault surface, and joins here.** Nothing before beat 11 needs it. An FTS5 virtual table over body text is additive and touches no existing table, so the day-one schema reserves nothing for it. What is decided now is only that the index is the home of full-text search — not a separate search library — so #140's editor decision can assume it.

**Update 2026-09-20 (beat 1b grill).** Decision 8's "only writer" is the index *module*, not the watcher batch: the app's own writes index themselves synchronously through the same module before the RPC returns, recording the hash that makes ADR 0013 decision 4's own-write no-op correct. Otherwise a captured Question would never reach the index — the watcher, recognising the app's hash, does nothing. Decision 2's pending-Revision rationale is deferred with the mechanism: beat 1b ships the `positionsOf` seam with no Kind registered, and beat 2 registers the first. Decision 7's "Markdown only" is about content: every non-dot file gets a `files` row so embeds and links to non-Markdown targets resolve. Decision 8's "one transaction per batch" is one per *chunk* of a batch: a batch over the chunk size commits in chunks, each raising `vaultChanged`, because outlining and `node:sqlite` are synchronous and a sync client delivering hundreds of files must not stall the core; the rebuild uses the same path. `vault.outline(path)` is assembled from the index, not a fresh outline. Details in `docs/architecture.md` § Index.

## Considered options

- **In-memory index rebuilt at open.** Rejected, decision 1.
- **`better-sqlite3`, or `sql.js` (WebAssembly).** Rejected, decision 1: the built-in exists and has FTS5.
- **Land the index at beat 2, or at beat 5.** Rejected, decision 2.
- **Fold the watcher ticket into beat 2's spec.** Rejected, decision 2.
- **Index for cross-file questions only; surfaces read files directly.** Rejected, decision 3.
- **One JSON outline per file.** Rejected, decision 5.
- **Store every `##` section's body so Positions fall out generically.** Rejected, decision 6.
- **Full rebuild on any change.** Rejected, decision 8.
- **Index the sidecar too.** Rejected, decision 7.
- **A "building index" screen at open.** Rejected, decision 10.

## Consequences

- **+** No new dependency and no native code; the index module is a file behind a seam, and swapping the engine would be one module.
- **+** One data-access posture for every surface still to come: Research Question view, Loose Ends, Coverage, the Vault surface all query the same tables, and none walks the vault.
- **+** Tier 5's precondition is a boolean the module owns, with a reason, instead of a judgement each caller makes.
- **+** "Safe to delete" is enforced by design: the rebuild path is the schema-change path, exercised on every migration rather than only in disaster.
- **−** A second store to keep coherent with the disk. The watcher batch is the only writer, and the after-commit event rule (decision 9) is what keeps a surface from reading stale rows; a refactor that raises `vaultChanged` earlier reopens that hole silently unless beat 1b's tests pin it.
- **−** On a large vault the first open after a schema change is a background rebuild during which tier 5 is conservative and lists may lag; by design, but visible.
- **−** The per-Kind `positionsOf` seam (decision 6) is the first place the index depends on Kind knowledge; a new Position-bearing Kind must register there or its external edits lose their `from:` text.
- The beat sequence in wayfinder map #131 gains **beat 1b — watcher and index**, specced by `to-spec` when its turn comes; the exact column list beyond the keys named here, and the footer copy, are that spec's to settle.
