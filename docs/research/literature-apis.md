# Literature APIs for Scouts and the attention scatter

Research note for [#132](https://github.com/tacomancy/vitrine/issues/132) (part of map #131). Answers three questions from the API docs themselves, then recommends one API for the first Structured-source Scout (beat 6) and one for the Question Map's growth-rate measure (beat 10).

Requirements this is checked against:

- Brief `## Scouts` → `### Proposals`: a Proposal is populated *from the source* — title, authors, publication date, venue, author-supplied keywords, abstract as published, link back. "Fields that cannot be extracted show as missing rather than guessed." Structured sources "return these fields directly."
- Brief `### Question Map` → Panel 2: "growth rate of publication volume, not absolute citation count", measured per Tag against a keyword set (the Lexicon, built from the author-supplied keywords on accepted papers), synced in the background with an "as of" indicator.
- `CONTEXT.md` § Scouts: a Structured source is queried with a Filter that becomes search terms deterministically; a Query is a hand-written search string.

Researched 2026-09-20 against the primary docs only (linked inline). Live spot-checks were run where a doc left a fact unstated; those are marked *observed*.

## arXiv

Docs: [API user manual](https://info.arxiv.org/help/api/user-manual.html), [terms of use](https://info.arxiv.org/help/api/tou.html), [basics](https://info.arxiv.org/help/api/basics.html), [OAI-PMH](https://info.arxiv.org/help/oa/index.html), [bulk data](https://info.arxiv.org/help/bulk_data.html).

**Search.** `http://export.arxiv.org/api/query?search_query=…`. Field prefixes `ti`, `au`, `abs`, `co` (comment), `jr` (journal ref), `cat`, `rn`, `all`; booleans `AND`, `OR`, `ANDNOT`; parentheses and quoted phrases. One date filter: `submittedDate:[YYYYMMDDTTTT TO YYYYMMDDTTTT]` in GMT. `sortBy` ∈ relevance / lastUpdatedDate / submittedDate. Paging via `start`/`max_results`; "the maximum number of results returned from a single call (max_results) is limited to 30000 in slices of at most 2000 at a time" and a request past 30,000 returns HTTP 400 (user manual §3.1.1.2).

**Fields returned** (Atom 1.0, user manual §3.3.2): `title`, `id`, `published` ("the date in which the first version of this article was submitted"), `updated`, `summary` (abstract), `author/name` with optional `arxiv:affiliation` ("If the author has supplied affiliation information"), `arxiv:comment`, `arxiv:journal_ref` ("If the author has provided a journal reference"), `arxiv:doi`, `arxiv:primary_category` and `category` ("used to describe either an arXiv, ACM, or MSC classification"), `link` rel=alternate (abs), rel=related (pdf, doi). Feed-level `opensearch:totalResults` "lists how many results are in the result set for the query".

Proposal mapping: title, authors, abstract, link — direct. Publication date is the arXiv submission date, not a venue date. Venue is free text and usually absent. **No author-keyword field exists**; categories are a controlled taxonomy (`cs.LG`), not author keywords.

**Auth and limits.** No key. ToU: "make no more than one request every three seconds, and limit requests to a single connection at a time", applied across "all of the machines under your control as a whole". The manual adds "there is no need to call the API more than once in a day for the same query" because results change only at the daily announcement. Metadata is CC0.

**Volume over time.** No count or facet endpoint. One call per (keyword set × month) with `submittedDate` bounds and `max_results=1`, reading `totalResults` — 720 calls ≈ 36 minutes at the ToU rate. Counts are by first-submission date. For offline computation, OAI-PMH (`https://oaipmh.arxiv.org/oai`, `arXiv`/`arXivRaw` formats, "does not support selective harvesting based on submission date") or the Kaggle metadata dump named on bulk_data.html.

## Semantic Scholar (Academic Graph API)

Docs: the ReDoc page at [api-docs/graph](https://api.semanticscholar.org/api-docs/graph) is a shell that renders [`/graph/v1/swagger.json`](https://api.semanticscholar.org/graph/v1/swagger.json) — quotes below are from that spec. Also [product page](https://www.semanticscholar.org/product/api), [tutorial](https://www.semanticscholar.org/product/api/tutorial), [license](https://www.semanticscholar.org/product/api/license).

**Search.** `/paper/search` — "A plain-text search query string. No special query syntax is supported. Hyphenated query terms yield no matches"; `limit` "Must be <= 100"; "Can only return up to 1,000 relevance-ranked results". `/paper/search/bulk` — "Text query that will be matched against the paper's title and abstract. All terms are stemmed in English"; syntax `+` AND, `|` OR, `-` NOT, `"…"` phrase, `*` prefix, `( )`, `~N` fuzziness/proximity; 1,000 per page via continuation `token`, up to 10,000,000 total; `sort` by paperId / publicationDate / citationCount. Filters on both: `year` (`2016-2020`, `2010-`), `publicationDateOrYear` (`YYYY-MM-DD:YYYY-MM-DD`, prefix `2020-06` = the month; "For records where a specific publication date is not known, they will be treated as if published on January 1st of their publication year"), `venue`, `fieldsOfStudy` (23 fixed values), `publicationTypes`, `openAccessPdf`, `minCitationCount`.

**Fields** (`fields=` parameter; default is `paperId,title` only): paperId, corpusId, externalIds ("limited to: ArXiv, MAG, ACL, PubMed, Medline, PubMedCentral, DBLP, and DOI"), url ("URL of the paper on the Semantic Scholar website"), title, abstract ("Note that due to legal reasons, this may be missing even if we display an abstract on the website"), venue, publicationVenue, journal, year, publicationDate ("YYYY-MM-DD"), publicationTypes, authors (authorId, name; `.affiliations` on request), fieldsOfStudy, s2FieldsOfStudy (classifier-assigned), openAccessPdf, citationCount, tldr (model-generated — the brief forbids using it on a Proposal), embedding.

Proposal mapping: title, authors, date, venue, link — direct. Abstract when present. **No keywords field exists anywhere in the spec.**

**Auth and limits.** Product page: "Most Semantic Scholar endpoints are available to the public without authentication, but they are rate-limited to 1000 requests per second shared among all unauthenticated users" and "Requests may also be further throttled during periods of heavy use." Keyed: "The introductory rate limit for an API key is 1 RPS on all endpoints"; key arrives by email from a request form. Header `x-api-key`. License (May 2023): non-sublicensable, no redistribution, attribution to "Semantic Scholar" required in published materials; third-party content (abstracts) carries its own licenses.

**Volume over time.** Bulk search returns `total` — "Approximate number of matching search results. Because of the subtleties of finding partial phrase matches in different parts of the document, be cautious about interpreting the total field as a count of documents containing any particular word in the query." One call per (keyword set × month) using `publicationDateOrYear=YYYY-MM`; 720 calls ≈ 12 minutes at 1 rps. No aggregation endpoint. Unknown-date papers pile into January. The index refresh cadence is not documented; dataset releases are roughly weekly.

## OpenAlex

Docs moved to `help.openalex.org` (the old `docs.openalex.org` URLs 301 there). Pages: [authentication](https://help.openalex.org/api/authentication/), [pricing](https://help.openalex.org/access/pricing/), [example costs](https://help.openalex.org/access/example-costs/), [searching](https://help.openalex.org/api/searching/), [filtering](https://help.openalex.org/api/filtering/), [grouping](https://help.openalex.org/api/grouping/), [paging](https://help.openalex.org/api/paging/), [work attributes](https://help.openalex.org/data/works/attributes/), [corpus](https://help.openalex.org/data/works/corpus/), [deprecations](https://help.openalex.org/api/deprecations/).

**Search.** `search=` covers "title, abstract, or fulltext"; uppercase `AND`/`OR`/`NOT`, quoted phrases, `"…"~N` proximity, stemming and stop-word removal (`search.exact` to disable). `filter=title.search:…`, `title_and_abstract.search:…`, `fulltext.search:…` (the older `default.search` is a deprecated alias). Whole request URL capped at ~4 KB — long OR-lists must be split and unioned client-side. Filters `from_publication_date` / `to_publication_date` / `publication_year`. `select=` trims fields. `per_page` max 100; basic paging to 10,000; `cursor=*` beyond that. `from_created_date` / `from_updated_date` are **paid-plan only** (filtering page § "Sync filters (paid plans)").

**Fields** (work attributes page): `title`/`display_name`; `authorships` ("Capped at the first 100 authors"); `publication_date` ("Where several dates exist, OpenAlex usually picks the earliest electronic-publication date"); `publication_year`; `primary_location` (best copy; `.source.display_name`, `.landing_page_url`); `doi` ("always holds the DOI of the published version"); `ids` (openalex, doi, mag, pmid, pmcid); `abstract_inverted_index` ("OpenAlex does not ship plaintext abstracts for legal reasons; reconstruct the abstract from the index. Newer works are more likely to have one (over 60% of 2022 works vs. ~45% of pre-2000 works)"; may carry "trailing text that isn't part of the abstract (section headings, keywords)"); `keywords` — **"Short phrases derived from the work's topics, each with a similarity score to the title and abstract"**; the [keywords page](https://help.openalex.org/data/keywords/) describes the pipeline as candidates gathered from the work's topics, scored against title and abstract with an embedding model, thresholded, top five kept; `topics` (up to three, classifier-assigned — "Text classifiers read each work's title and abstract to decide what it's about", [how it's built](https://help.openalex.org/data/how-its-built/)); `concepts` (legacy); `authorships[].raw_author_name` ("The author's name exactly as it appeared on the source record"); `updated_date`, `created_date`. `host_venue` is removed. Public snapshot is quarterly and free (S3, no account); the daily snapshot is a paid tier.

Proposal mapping: title, authors, date, venue, link — direct. Abstract is reconstructable text, which the brief's "as published" tolerates less well than a verbatim string but is still the source's text, not a model summary. **`keywords` are not author-supplied** — they are derived from OpenAlex's own topic classification and must not be fed to the Lexicon as if they were.

**Auth and limits.** Since February 2026 the polite pool is gone ("The mailto parameter is ignored") and replaced by a per-account credit budget. "You can make basic queries with no key at all"; "a free key gives you 10× the keyless budget"; "Two things return 429 Too Many Requests: exceeding your daily budget, or making more than 100 requests per second." Budgets: keyless $0.10/day, free key $1/day, resets midnight UTC. Per-operation cost (example-costs page): single entity free; "List + filter" $0.10 per 1,000 calls (1 credit); "Search" $1 per 1,000 (10 credits). Every response carries `X-RateLimit-Limit`, `-Remaining`, `-Credits-Used`, `-Reset`. Key is a query param or `Authorization: Bearer`. Data is CC0. Corpus: "more than 320 million works built and matched from Crossref, MAG, PubMed, DataCite, repositories, and more" in the default core; a rawer 190M-work "expansion" is behind a flag.

**Volume over time.** `group_by=publication_year` "aggregates entities into groups and counts how many are in each group" and combines with any filter; `meta.count` is "Total entities matching the filter". Groups are capped at 200 per page (irrelevant for years). Grouping by `publication_date` is refused ("Cannot group by date, number, or search fields" — *observed*), so monthly buckets need one call per month window with `from_publication_date`/`to_publication_date`.

*Observed 2026-09-20, keyless:* `works?filter=title_and_abstract.search:"sparse autoencoder",from_publication_date:2023-01-01&group_by=publication_year` returned four year buckets in one call at `x-ratelimit-credits-used: 1` ($0.0001). The same filter over a single month with `group_by=publication_year` also cost 1 credit; the same month as a plain list call (`per_page=1`) cost 10 credits. So the cheap shape is *filter + group_by*, never a bare list. 20 keyword sets × 36 monthly windows = 720 credits ≈ $0.07 — within the $0.10 keyless daily budget, and 7% of the free-key budget. Per-year: 20 calls. `meta.count` is not documented as exact or approximate; unlike Crossref and Semantic Scholar, no caveat is attached.

## Crossref REST API

Docs: the live spec at [`api.crossref.org/swagger-docs`](https://api.crossref.org/swagger-docs) (rendered by [swagger-ui](https://api.crossref.org/swagger-ui/index.html)); [REST API overview](https://www.crossref.org/documentation/retrieve-metadata/rest-api/); [tips](https://www.crossref.org/documentation/retrieve-metadata/rest-api/tips-for-using-the-crossref-rest-api/); [access and authentication](https://www.crossref.org/documentation/retrieve-metadata/rest-api/access-and-authentication/); [filters](https://www.crossref.org/documentation/retrieve-metadata/rest-api/rest-api-filters/). The GitHub [rest-api-doc README](https://github.com/CrossRef/rest-api-doc) carries a banner "This documentation is deprecated"; it is cited below only where the live docs are silent.

**Search.** `query` — "Search queries can be made to look for the presence of one or more words in any field"; field queries `query.bibliographic` ("titles, authors, ISSNs and publication years"), `query.author`, `query.container-title`, `query.affiliation`, etc. This is relevance matching, not boolean: *observed*, `query.bibliographic=sparse autoencoder interpretability&rows=0` reports `total-results: 95228`, i.e. any-word matching. Filters `from-pub-date`/`until-pub-date` (year, month, or day granularity), `from-created-date`, `from-index-date` (the one to use for sync), `type`, `has-abstract`. `select=` for fields. `rows` up to 1000, `rows=0` for summary only; `offset` up to 10,000; `cursor=*` for deep paging, cursors "expire after 5 minutes if not used". `sort=published&order=asc`.

**Fields** (Work schema in the spec; definitions in the README's api_format.md): `title` (array), `author` (given, family, affiliation, ORCID, sequence), `issued` ("Earliest of published-print and published-online"), `published-print`, `published-online`, `created` (DOI registration date, not publication), `container-title` (venue), `abstract` ("Abstract as a JSON string or a JATS XML snippet encoded into a JSON string" — deposited by members who choose to, coverage tracked per member in Participation Reports), `subject` ("Subject category names, a controlled vocabulary from Sci-Val" — a journal-level classification, not author keywords), `DOI`, `URL` (DOI resolver form), `link` (full-text URLs), `type`.

Proposal mapping: title, authors, `issued` date, venue, DOI link — direct. Abstract only where deposited (filter `has-abstract` to know). **No author-keyword field exists.**

**Auth and limits.** "Anyone can access the REST API, no signup or registration is required." Three pools (access page): Public — limit 5, concurrency 1; Polite — `mailto=` param or contact in `User-Agent`, limit 10, concurrency 3; Metadata Plus (paid token) — 150. The page does not print the unit; "Any rate limits that are in effect will be advertised in the X-Rate-Limit-Limit and X-Rate-Limit-Interval HTTP headers" (README), 429 on excess. License: "Almost none of the metadata is subject to copyright, and you may use it for any purpose. Some abstracts contained in the metadata may be subject to copyright by publishers or authors." Freshness (README): "Records typically appear in the REST API within 20 minutes"; "Summary information (e.g. counts, etc.) are processed in batch every 24 hours."

**Volume over time.** `facet=published:*` returns "Earliest year of publication" counts in one `rows=0` call — but "Note that facet counts are approximate and may differ from exact counts obtained using filters" (spec). Year granularity only; months need one filtered `rows=0` call each (720). The bigger problem is upstream: since `query` is any-word relevance matching, a "keyword set" cannot be expressed as a boolean and the count measures something looser than the other APIs do.

## PubMed via NCBI E-utilities

Docs: [E-utilities help (NBK25497)](https://www.ncbi.nlm.nih.gov/books/NBK25497/), [E-utilities in depth (NBK25499)](https://www.ncbi.nlm.nih.gov/books/NBK25499/), [sample applications (NBK25498)](https://www.ncbi.nlm.nih.gov/books/NBK25498/), [PubMed User Guide](https://pubmed.ncbi.nlm.nih.gov/help/), [NCBI policies](https://www.ncbi.nlm.nih.gov/home/about/policies/), [NCBI Insights: API keys](https://ncbiinsights.ncbi.nlm.nih.gov/2017/11/02/new-api-keys-for-the-e-utilities/), MEDLINE/PubMed element descriptions ([Archive-It capture 2024-02-20](https://wayback.archive-it.org/org-350/20240220194809/https://www.nlm.nih.gov/bsd/mms/medlineelements.html) — the live NLM page now redirects there). The Bookshelf pages serve a browser check to plain HTTP clients; they were read through a browser.

**Scope.** "The PubMed database contains citations and abstracts to biomedical literature" (User Guide) — MEDLINE, PMC, Bookshelf. Nothing outside the life sciences; general-science articles off-topic for MEDLINE are not indexed.

**Search.** Two calls minimum — "A text search in web Entrez is equivalent to ESearch-ESummary" (NBK25497); none of the nine utilities returns records from a text query. ESearch (`esearch.fcgi?db=pubmed&term=…`) returns PMIDs and a `Count`; EFetch (`efetch.fcgi?db=pubmed&id=…&retmode=xml`) or ESummary returns records, by `id` list or `query_key`+`WebEnv`. Term syntax `term1[field1] Op term2[field2]` with `AND`/`OR`/`NOT` "in all capital letters". Field tags from the User Guide: `[tiab]` — "title, collection title, abstract, other abstract and author keywords (Other Term [ot] field)"; `[ot]` — "The author keyword field (OT field) is searchable with the title/abstract [tiab], text word [tw] and other term [ot] search tags. To retrieve all citations that have keywords, use the query haskeyword"; `[mh]` MeSH; dates `[dp]` "Includes both print and electronic dates of publication except for electronic publication dates occurring after the print publication date", `[edat]`, `[crdt]` ("often more comprehensive than Publication Date [dp] when checking PubMed on a regular basis for new citations"), ranges as `2019/01/01:2019/06/30[dp]`. ESearch also takes `datetype` (`pdat`, `edat`, `mdat`), `mindate`/`maxdate` ("YYYY/MM/DD… YYYY, YYYY/MM"), `reldate`, `sort=pub_date|relevance`, `rettype=count`, and `retmax` — "For PubMed and PMC, ESearch can only retrieve the first 10,000 records matching the query"; segment by date to get past it. Untagged terms go through Automatic Term Mapping; a tag or quotes bypass it.

**Fields** (PubMed XML via EFetch, element descriptions): `ArticleTitle`; `AuthorList/Author` with `AffiliationInfo` ("provided as supplied by the publisher", all authors since December 2014); `Journal/Title` (venue, "taken from NLM's cataloging data"); `PubDate` — "the data are taken as they are published in the journal issue", so `2001` or `2000 Spring` are valid, with `MedlineDate` when unparseable — and `ArticleDate DateType="Electronic"`; `Abstract/AbstractText` — "English-language abstracts are as supplied by the publisher or taken directly from the published article. If the article does not have a published abstract, the National Library of Medicine does not create one", `Label`/`NlmCategory` attributes for structured abstracts; **`KeywordList Owner="NOTNLM"`** — OT: "This field contains largely non-MeSH subject terms (also referred to as Keywords) that describe the content of the article. Beginning in January 2013, author-supplied keywords are included in Other Term", owner `NOTNLM` = "The journal publisher or other data provider. This is used when the OT field includes author-supplied keywords"; `MeshHeadingList` — indexer-assigned ("whatever the author's words"), absent on `publisher` and `inprocess` status records; `ELocationID EIdType="doi"` / `ArticleIdList`; `PMID` → `https://pubmed.ncbi.nlm.nih.gov/<PMID>/`.

Proposal mapping: every field the brief asks for, including author keywords — the only API of the five that can. Keywords are absent before 2013 and whenever the publisher did not supply them (`haskeyword` filters to those); no doc quantifies how often. Filter `KeywordList` by `Owner` — KIE/NASA/PIP-owned lists are not author keywords.

**Auth and limits.** NBK25497: "Without an API key, any site (IP address) posting more than 3 requests per second to the E-utilities will receive an error message. By including an API key, a site can post up to 10 requests per second by default." Key from "the Settings page of their NCBI account", "Only one API key is allowed per NCBI account", sent as `api_key=`. "limit large jobs to either weekends or between 9:00 PM and 5:00 AM Eastern time during weekdays"; the policies page says this applies to "any series of more than 100 requests". `tool=` and `email=` "should be included in all E-utility requests" and "must be registered with NCBI" by emailing eutilities@ncbi.nlm.nih.gov. Base URL must be `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/`. "NLM does not claim the copyright on the abstracts in PubMed; however, journal publishers or authors may." Freshness: "New citations from MEDLINE journals are received electronically from publishers and appear in PubMed daily"; records climb `publisher[sb]` → `inprocess[sb]` → `medline[sb]`, and MeSH arrives only at the last step — so "no MeSH" on a fresh item is not "no subject".

**Volume over time.** `rettype=count` "displays only the <Count> tag"; `Count` is "total number of records matching query" (NBK25500) with no estimate caveat. *Observed:* `esearch.fcgi?db=pubmed&term=sparse+autoencoder&rettype=count&datetype=pdat&mindate=2025/01/01&maxdate=2025/12/31` returned `<Count>121</Count>` in one call. Booleans and field tags make the keyword set precise. No facet endpoint (EGQuery counts per *database*, not per date), so 720 calls ≈ 4 minutes at 3 rps — and past 100 requests the off-peak rule technically applies. `[dp]` can carry two years for one citation, so month buckets can shift at year boundaries. Biomedical coverage only, so this measures the field only for a life-sciences user.

## Recommendations

### First structured Scout (beat 6): **arXiv**

Reasons, in order of weight:

1. **It is where the user's field publishes first.** The Scout's job is to surface *new* work; arXiv is the preprint venue for CS/ML/physics, and the brief's own example Scouts ("Semantic Scholar + arXiv", the Anthropic Alignment output) point here. Semantic Scholar and OpenAlex both ingest arXiv, so starting upstream loses nothing and adds a day or two of freshness.
2. **Zero auth, zero budget, stable terms.** No key, no daily credit meter, CC0 metadata, and a ToU cadence (one request per three seconds, daily is enough) that matches a daily-to-monthly Scout exactly. Semantic Scholar's keyless pool is shared with every anonymous user on the internet and "may be further throttled"; OpenAlex's keyless $0.10/day is fine but is a metered account to explain in a BYOK-flavoured app. arXiv asks for nothing.
3. **Fields come back verbatim and complete.** Title, every author, the abstract as the author wrote it, the abs/PDF/DOI links, in one Atom response — no `fields=` negotiation, no inverted index to reconstruct, no "may be missing for legal reasons". Where a field is absent (venue, keywords) it is absent at the source, which is exactly the "missing, not guessed" state the brief wants a card to show.
4. **The query language fits the Filter model.** `ti:`/`abs:` prefixes, `AND`/`OR`/`ANDNOT`, quoted phrases and `submittedDate` ranges let a Question's Lexicon terms be compiled deterministically into a query with no model call, as `CONTEXT.md` § Filter requires. Semantic Scholar's relevance endpoint has "no special query syntax"; its bulk endpoint does but returns 1,000 unsorted-by-relevance rows per page, which is the wrong shape for a Scout.

Cost of this choice: no author keywords (true of every non-PubMed API) and no venue for most items. The second structured source should be Semantic Scholar or OpenAlex to add venue and the eventual journal record for dedup's "most complete metadata wins" — that is a later beat.

### Growth-rate measurement (beat 10): **OpenAlex**

1. **It is the only one of the five with server-side aggregation.** `filter=…&group_by=publication_year` returns the whole per-year series for a keyword set in one request; the others need one call per bucket. Per month it is still one tiny call per window, and the observed cost is 1 credit each — 20 Tags × 36 months ≈ $0.07, inside the *keyless* daily budget, and per-year refreshes are 20 calls. A free key makes it a rounding error.
2. **The count is a count of documents matching a boolean, over the broadest cross-discipline corpus.** `title_and_abstract.search` takes `AND`/`OR`/`NOT` and phrases, so a Tag's Lexicon compiles to one query; `meta.count` carries no "approximate" caveat (Semantic Scholar's `total` and Crossref's facets are documented as estimates; Crossref's `query` is any-word matching so the set is ill-defined). 320M works across every field beats arXiv's preprint-only and PubMed's biomedical-only windows for a general-purpose app.
3. **It carries the "as of" the brief asks for.** `updated_date`/`created_date` on works and a daily-refreshed index give the panel an honest timestamp; the `X-RateLimit-*` headers on every response let the sync report its own budget use, which keeps a broken sync from looking like a quiet field.
4. **Same source for all Tags.** Growth *rate* only compares meaningfully when every Tag is measured against the same corpus. One API for the whole scatter matters more than the best API per Tag.

Caveats to carry into the beat-10 grill: OpenAlex `publication_date` is the earliest electronic date, so the current year's bucket is partial and must be shown as such; `group_by` cannot bucket by month, so monthly needs windows; the credit model is new (February 2026) and is a pricing surface that could move; and a keyless client shares nothing with the user's identity, which is the right default for BYOK.

## What this changes for the Lexicon

The brief's `#### The tag lexicon` builds each Tag's keyword set from "the author-supplied keywords" on accepted papers. Of the five Structured sources, only PubMed returns those, and only for biomedical papers. For the CS/ML literature the brief's examples come from, **no API will hand over author keywords** — arXiv has none, Semantic Scholar and Crossref have no field, OpenAlex's `keywords` are machine-derived from its topic model.

Options the beat-10 grill will have to choose between, listed by reversibility:

- Build the Lexicon from title and abstract terms of accepted papers instead (TF-IDF or similar over the vault's own Sources) — deterministic, source-agnostic, and most reversible since it needs no API.
- Take author keywords from the PDF itself at ingest, where the paper prints them — the brief already has the PDF; many venues put keywords under the abstract.
- Accept OpenAlex `keywords`/`topics` as a *labelled* machine vocabulary, shown as such in the Lexicon editor — least faithful to the brief's wording, but the brief's "visible and editable" rule makes the provenance legible.

This belongs in `CONTEXT.md` § Lexicon and an ADR once decided; it is recorded here only as the finding.
